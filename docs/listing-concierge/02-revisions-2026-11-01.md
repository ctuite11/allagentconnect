# Listing reminders + Concierge — revisions approved by Chris, 2026-11-01

STATUS: SPEC ONLY. Build and test in Nenad's separate Supabase/Netlify environment. Nothing goes to production, no reminders are switched on, and no emails are sent without Chris's explicit approval.

## 1. Concierge form reuses Edit Listing
- The status menu is the existing `ADD_LISTING_EDIT_STATUSES` (`src/constants/status.ts`) with the same labels and order: Off Market, Coming Soon, Active, Back on Market, Pending, Temporarily Withdrawn, Expired, Cancelled, Sold. Use the same `handleStatusChange` behavior as `EditListing.tsx`: Withdrawn shown disabled when current, Coming Soon needs a go-live date, New uses auto-activate days.
- Pre-fill the listing's current status, price, photos and details from the listing row.
- Split the field components out of `EditListing.tsx` into one shared `ListingEditFields` component, used by both Edit Listing and the concierge form. Use the same validation, without a second copy.
- The proposal stores a diff only (`listing_concierge_requests.proposed_changes jsonb`, which replaces the `update_type` enum and keeps it as legacy). Approval applies it through the same save path as Edit Listing, writing `listing_status_history` and `listing_price_history`.
- Sold requires: `sold_closing_date` (date, not in the future), `sold_price` (> 0), and `buyer_agent_comp_paid_type` in (`percent`,`amount`,`none`,`unknown`), plus `buyer_agent_comp_paid_value` when the type is percent or amount. These record compensation actually PAID. Never copy the offered compensation into them. Enforce with a CHECK constraint and in the form.

## 2. Assistant copies
- Recipients = the listing agent + every `agent_account_members` row with `owner_user_id = listing.agent_id`, `status='accepted'`, `revoked_at IS NULL`, and its `delegate_user_id` email.
- Each recipient gets an individual `email_jobs` row (no CC). Idempotency key: `concierge:<event>:<request_or_listing_id>:<lower(email)>`. Dedupe recipients by lowercase email before enqueueing, so an agent who is also listed as someone's assistant gets one email.
- Check `email_unsubscribes` for each recipient separately (category `all` or `listing_reminders`). If the agent has unsubscribed, the assistant still gets their copy, and the other way round.
- Events: `reminder`, `request_received`, `review_ready`, `published`. The staff email (`staff_new_request`) goes to staff only.
- Permissions: every action calls the existing `can_act_for_agent(listing.agent_id)` / `effective_agent_id()`. This adds no new assistant restrictions and widens none. Links in the assistant copy lead to the same sign-in-protected pages, and access is decided after sign-in, never by the link.
- `listing_reminder_candidates()` returns one row per (listing, recipient) for sending. `claim_listing_reminder(listing_id)` still claims per LISTING, so all of one listing's recipients go out in the same run, and none go out again within 30 days.

## 3. "Yes, It's Still Accurate"
- Link → `/agent/listings/:id/confirm` (signed in). The page checks `can_act_for_agent`, then calls `confirm_listing_accurate(listing_id)`, which records `confirmed_at`, `confirmed_by` and sets `agent_last_touched_at = now()`. This removes the listing from the never-updated campaign. Clicking again changes nothing. The link carries no token that grants access.

## 4. Concierge from Edit Listing
- A "Let Our Concierge Handle It" button on Edit Listing opens `/agent/listings/:id/concierge`, the same route, form, table and emails as the reminder-email path. `listing_concierge_requests.source` in (`reminder_email`,`edit_listing`).
